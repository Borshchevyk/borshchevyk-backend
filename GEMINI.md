# Borshchevyk Backend

## Описание проекта
Borshchevyk — это серверная часть современного offline-first мессенджера (аналог Telegram). Проект спроектирован с упором на надежность, высокую производительность, безопасность и работу в условиях нестабильного или отсутствующего интернет-соединения (с прицелом на будущую поддержку mesh-сетей). 

Бэкенд обеспечивает:
*   Регистрацию и сквозную криптографическую авторизацию (Challenge-Response).
*   Управление профилями пользователей, списком контактов и детальными настройками приватности.
*   Работу личных чатов, групп и каналов с гибкой ролевой моделью и гранулярными правами доступа.
*   Мгновенную доставку сообщений через WebSockets (STOMP) и брокеры сообщений.
*   Синхронизацию данных (Event Sourcing) для клиентов, которые долго находились в оффлайне, через выделенный сервис синхронизации.

## Технологический стек
*   **Язык:** Java 21
*   **Фреймворк:** Spring Boot 3 (Web, Data JPA, Security, Cloud Gateway, WebSockets)
*   **Базы данных:** PostgreSQL 16 (Основное хранилище)
*   **Кеширование и Pub/Sub:** Redis 7 (Хранение временных токенов, масштабирование WebSockets)
*   **Брокер сообщений:** Apache Kafka 7.3.2 (Асинхронное взаимодействие микросервисов, Event Sourcing) + Zookeeper
*   **Маппинг объектов:** MapStruct
*   **Документация:** OpenAPI (Swagger 3)
*   **Инфраструктура:** Docker, Docker Compose
*   **Reverse Proxy / SSL:** Caddy (Автоматическая терминация HTTPS сертификатов)

## Архитектура
Бэкенд построен на основе микросервисной архитектуры. Точкой входа является API Gateway, который маршрутизирует запросы и проверяет JWT-токены. 

Каждый микросервис строго следует принципам **Гексагональной Архитектуры (Ports and Adapters)** и Domain-Driven Design (DDD).

### Структура папок микросервиса:
```text
src/main/java/ru/kubsu/borshchevyk/<service>/
├── domain/                  # Ядро бизнеса (Никаких зависимостей от фреймворков, чистая Java)
│   ├── model/               # Сущности (Entities) и Value Objects (например, UserId)
│   ├── event/               # Доменные события (Domain Events)
│   └── exception/           # Бизнес-исключения
├── application/             # Слой сценариев использования (Use Cases)
│   ├── dto/                 # Входные и выходные данные для Use Cases (Commands, Results)
│   ├── port/in/             # Inbound Ports (Интерфейсы Use Case'ов)
│   ├── port/out/            # Outbound Ports (Интерфейсы для БД, брокеров, внешних API)
│   └── service/             # Имплементация Use Case'ов (Бизнес-логика, оркестрация портов)
└── infrastructure/          # Слой адаптеров (Связь с внешним миром и фреймворками)
    ├── adapter/in/web/      # Входящие адаптеры: REST Контроллеры, DTO запросов/ответов, Мапперы
    ├── adapter/in/messaging/# Входящие адаптеры: Kafka Listeners (Консюмеры)
    ├── adapter/out/persistence/ # Исходящие адаптеры: JPA Entities, Repositories, реализация портов БД
    ├── adapter/out/messaging/   # Исходящие адаптеры: Kafka Publishers (Продюсеры)
    └── config/              # Конфигурации Spring (Security, WebSockets, Beans)
```
*Главное правило:* Зависимости направлены только внутрь (к слою `domain`). `domain` ничего не знает про `application`, а `application` ничего не знает про SQL, HTTP или Kafka (всё общение идет через интерфейсы-порты).

## CI/CD и Развертывание
Развертывание полностью автоматизировано через **GitHub Actions**.

### Процесс (Workflow):
1.  **Build & Push (на серверах GitHub):** При пуше в ветку `dev`, GitHub Actions поднимает изолированную среду с Java 21 и Maven, компилирует все 4 микросервиса (`auth`, `user`, `message`, `sync`, `gateway`). Затем пакует скомпилированные `.jar` файлы в легковесные Docker-образы (`eclipse-temurin:21-jre-alpine`) и загружает их в приватный **GitHub Container Registry (GHCR)**.
2.  **Deploy (на целевом VPS):** После успешной сборки GitHub Action подключается к рабочему серверу по SSH (используя пароль).
3.  **Оркестрация:** На сервере экшен создает безопасный файл `.env` из секретов GitHub (чтобы скрыть пароли и порты от публичного репозитория), авторизуется в GHCR, скачивает новые, уже собранные Docker-образы (`docker-compose pull`) и атомарно перезапускает контейнеры (`docker-compose up -d`).
4.  **Очистка:** Удаляются старые неиспользуемые образы (`docker image prune`), чтобы сервер не забился мусором.

### Безопасность и Сеть
*   Внешний мир имеет доступ **только** к портам 80 (HTTP) и 443 (HTTPS), которые слушает Caddy.
*   Caddy автоматически получает и обновляет SSL-сертификат для домена, расшифровывает трафик и перенаправляет его во внутреннюю сеть Docker на API Gateway (порт 8080).
*   Базы данных (PostgreSQL, Redis), Zookeeper и Kafka, а также сами микросервисы **не имеют открытых портов наружу**. Они общаются друг с другом исключительно в изолированной виртуальной подсети Docker-Compose.
